# DESIGN_RULES.md

## Назначение

Этот файл содержит обязательные правила визуального дизайна проекта.

Все правила обязательны к исполнению.
Любое нарушение считается **дефектом** и должно быть исправлено.

Правила нельзя заменять собственными дизайнерскими решениями без явного разрешения.

---

## 1. Запретный список хранится в файле

Полный список запрещённых визуальных приёмов должен находиться в `DESIGN.md`.

Не держать ограничения только в памяти или в контексте задачи.

В `DESIGN.md` должна быть таблица:

| Нельзя | Почему |
|---|---|
| ... | ... |

При обнаружении запрещённого приёма считать это дефектом и исправлять.

**Правило:** если ограничение не зафиксировано в файле, оно не считается частью дизайн-контракта.

---

## 2. Два маркера ИИ-слопа запрещены

Запрещены следующие приёмы:

### 2.1. Мелкий текст капсом с разрядкой

Не использовать декоративные подписи вида:

`LIVE GRAPH`

`SENSOR SYNC`

`SYSTEM STATUS`

`REAL-TIME DATA`

Особенно в формате:

`L I V E   G R A P H`

Мелкий капс с большим расстоянием между буквами не использовать как декоративный способ создания «технологичности».

### 2.2. Точка-разделитель в метаданных

Не использовать конструкцию:

`1 месяц • в наличии • гарантия`

`React • Next.js • TypeScript`

`2026 • Москва • Full-time`

Если несколько характеристик необходимо показать рядом, использовать нормальную структуру интерфейса: отдельные элементы, строки, колонки или визуальные группы.

**Правило:** эти два приёма запрещены независимо от контекста.

---

## 3. Один акцент на экран

Основа интерфейса — почти монохромная тёмная палитра.

На одном экране допускается **один основной акцентный цвет**.

Акцент используется только в трёх случаях:

1. главное действие;
2. критически важное число;
3. ошибка / предупреждение.

Не заливать акцентным цветом большие области интерфейса без функциональной необходимости.

Не использовать одновременно несколько ярких акцентных цветов.

**Цель:** цвет должен обозначать важность, а не украшать интерфейс.

---

## 4. Никакого текста без функции

Каждый текстовый элемент должен выполнять конкретную задачу.

Запрещены:
- декоративные слоганы;
- пустые манифесты;
- очевидные описания;
- текст ради заполнения пространства;
- подписи, которые ничего не добавляют к пониманию интерфейса.

### Проверка

Перед сдачей удалить каждый текстовый элемент по очереди.

Если после удаления ничего не ухудшилось и ничего не стало менее понятным — текст был лишним.

Удалить его.

**Правило:** текст существует только тогда, когда без него интерфейс теряет смысл, контекст или возможность действия.

---

## 5. Стекло используется только по необходимости

Размытие фона (`blur`) разрешено только там, где под элементом действительно находится изменяющийся или важный контент.

Допустимые случаи:
- навигация;
- шторки;
- модальные окна;
- плавающие элементы поверх контента.

Не использовать стеклянный эффект как стандартный стиль карточек.

Запрещено создавать карточки исключительно через:

- прозрачный фон;
- `backdrop-filter`;
- размытие;
- слабую границу;
- свечение.

Карточка должна иметь самостоятельную визуальную структуру.

**Правило:** стекло — функциональный инструмент, а не декоративный стиль проекта.

---

## 6. Дефолтный shadcn запрещён

Нельзя использовать стандартный внешний вид компонентов `shadcn/ui` без существенной визуальной адаптации.

Запрещено оставлять компоненты в состоянии «установил библиотеку и использовал как есть».

При использовании готовых компонентов обязательно кастомизировать:
- размеры;
- отступы;
- радиусы;
- границы;
- цвета;
- типографику;
- состояния;
- композицию.

Компонент должен соответствовать визуальной системе проекта.

**Правило:** техническая библиотека может использоваться, но её стандартный внешний вид не является дизайном проекта.

---

## 7. Понятность важнее красоты

Любое дизайнерское решение оценивается прежде всего по тому, насколько быстро пользователь понимает его назначение.

Если визуально красивый элемент ухудшает понимание — убрать или изменить его.

Пример:

Если переключатель тарифов в виде чипов выглядит красиво, но на реальном каталоге непонятно, что именно переключается, использовать более очевидный элемент управления.

Если отдельная серая кнопка `Недоступно` не сообщает ничего нового и занимает место рядом с главным действием, убрать её и оставить понятное состояние непосредственно в интерфейсе.

### Правило проверки

Для каждого нестандартного элемента задать вопрос:

**«Поймёт ли новый пользователь его назначение без объяснения?»**

Если нет — упростить.

**Приоритет:**

`Понятность → функция → иерархия → эстетика → декоративность`

# Контроль перед сдачей

Перед завершением каждого экрана проверить:

- [ ] нет запрещённых приёмов из `DESIGN.md`;
- [ ] нет мелкого капса с разрядкой;
- [ ] нет точек-разделителей в метаданных;
- [ ] используется не более одного акцентного цвета;
- [ ] акцент имеет функциональную причину;
- [ ] нет текста без функции;
- [ ] стекло используется только там, где оно действительно необходимо;
- [ ] нет стандартного внешнего вида `shadcn/ui`;
- [ ] нестандартные элементы понятны без объяснений;
- [ ] декоративные элементы не конкурируют с основным действием.

**Любой пункт, который не пройден, является дефектом.**
